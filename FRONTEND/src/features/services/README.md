# Services workspace

Services is a real operational view over existing SIG-DESK domains.

- **Work order:** an RFC Task whose assignment snapshot points to the Services
  department. Change Management owns the record and its lifecycle.
- **Site and equipment:** read from the Assets/CMDB projection owned by
  `resource_service`.
- **Operational history:** composed from the existing INC, PRB and RFC asset
  context endpoints.
- **Authorization:** `change_tasks:read` opens work orders,
  `change_tasks:update` executes them, `assets:read` opens sites, and
  `changes:read` controls the optional link to the full RFC.

`api.ts` is intentionally a thin integration façade. It must not copy backend
rules into a new Services-only state machine. `presentation.ts` only maps the
authoritative Task state to labels, actions and deadline presentation.

Required tasks cannot be canceled because the RFC close invariant requires
them to finish with evidence. Optional tasks may be canceled with a reason.
The Change workspace hides an invalid cancellation action, while
`change_service` enforces the rule for every client.

Open Work Orders with a deadline are scanned by `change_service`. Reaching the
deadline emits `RFCTareaVencida` through its transactional outbox exactly once
per deadline; Notification routes it to the assignee, or to the destination
team when no individual assignee exists. Changing the deadline rearms the
notification without duplicating the previous one.

When this capability is first deployed over an existing database, historical
deadlines are acknowledged by a one-time migration without emitting a backlog
storm. New and rescheduled deadlines are notified normally.

The removed prototype concepts—`SRV-*` records, dealerships, POCs,
subcontractors, quotes and invoices—must not return as local state or fixtures
in production code. Add one only after its owner, persistence, permissions,
audit contract and API have been defined.

A direct service request that does not require a governed change belongs to the
future RQS / Request Fulfillment domain. It is intentionally not disguised as
an RFC Task: this workspace currently covers executable work authorized by an
RFC, while RQS still needs its own persistent backend contract.

Team-directed Work Orders are claimed atomically when a member selects **Start**.
Organization validates that the actor belongs to the approved department and
team; a failed validation leaves the assignment, state, and event outbox
unchanged. The UI displays the trusted assignee-name snapshot and never exposes
the stable user UUID as a label. Tasks generated by the approved operational
pack cannot be edited into optional work or canceled to bypass RFC governance.

## Beta verification

`e2e/itsm-golden-path.spec.ts` exercises the workspace against disposable,
real Tickets, Problem and Change service processes. It creates and approves an
RFC, creates an Inventory prerequisite and a Services Work Order, then signs in
as the actual Services assignee with only `change_tasks:read:propio` and
`change_tasks:update:propio`. Through the UI it starts, blocks, clears the
blocker, restarts, completes with evidence, reopens and completes the Work Order
again before the RFC closes. The unrelated Inventory task and the full RFC link
remain unavailable to that identity.

`e2e/services-workspace.spec.ts` complements that live-backend journey with
bounded UI cases for Assets/CMDB composition, mixed device types, permissions
and controlled dependency failures. Both specs are part of the official beta
release gate.
